Python Context Managers: Write Cleaner, Safer Code with the with Statement

If you followed this series, you already know how to read and write files with open(). You probably wrote something like this:

f = open("data.txt")
text = f.read()
f.close()

It works, but it has a quiet flaw: if an exception fires between open() and close(), the file never gets closed. Leaked file handles, locked resources, half-written data. The classic fix is try/finally:

f = open("data.txt")
try:
    text = f.read()
finally:
    f.close()

Correct, but noisy. Python gives us a cleaner answer: the with statement and the objects behind it, context managers.

The with Statement in One Idea

A context manager is any object that defines two methods: __enter__ and __exit__. The with statement calls __enter__ when the block starts and __exit__ when it ends, even if an exception blows up in the middle.

with open("data.txt") as f:
    text = f.read()
# file is closed here, guaranteed

That is the whole contract: setup on entry, guaranteed cleanup on exit. Files are just the most famous example. The pattern shows up everywhere once you start looking: thread locks, database transactions, temporary directory changes, timers.

Context Managers You Already Use

The standard library is full of them. A threading.Lock releases itself:

import threading
lock = threading.Lock()

with lock:
    # only one thread runs this block at a time
    update_shared_counter()

The decimal module lets you scope precision changes so they never leak into the rest of your program:

from decimal import Decimal, localcontext

with localcontext() as ctx:
    ctx.prec = 50
    result = Decimal(1) / Decimal(7)
# precision is back to normal here

Writing Your Own: The Class-Based Way

Suppose you want a simple timer for profiling code blocks. Define the two dunder methods:

import time

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        elapsed = time.perf_counter() - self.start
        print(f"Elapsed: {elapsed:.3f}s")
        # returning False (or nothing) lets exceptions propagate
with Timer():
    run_expensive_computation()
# Elapsed: 2.314s

Notice the three arguments of __exit__. They carry the exception details if one occurred, or None if the block finished cleanly. If __exit__ returns a truthy value, it suppresses the exception. That is powerful and easy to abuse, so suppress deliberately, not by accident.

The Easy Way: contextlib.contextmanager

Writing a class for every small setup/teardown pair gets tedious. The contextlib module turns a generator function into a context manager. Everything before yield is setup, everything after is cleanup:

from contextlib import contextmanager

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield
    finally:
        elapsed = time.perf_counter() - start
        print(f"Elapsed: {elapsed:.3f}s")
with timer():
    run_expensive_computation()

The try/finally inside the generator is the key: it guarantees cleanup runs even when the with block raises. This decorator form covers the vast majority of custom context managers you will ever write.

contextlib ships a few more tools worth knowing:

from contextlib import suppress, redirect_stdout
import io

# ignore a specific exception instead of try/except/pass
with suppress(FileNotFoundError):
    os.remove("temp.txt")

# capture printed output
buf = io.StringIO()
with redirect_stdout(buf):
    print("hello")
captured = buf.getvalue()  # "hello\n"

A Real-World Pattern: Database Transactions

Here is where the pattern earns its keep. A transaction must commit on success and roll back on failure, with no forgotten branches:

import sqlite3
from contextlib import contextmanager

@contextmanager
def transaction(db_path):
    conn = sqlite3.connect(db_path)
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()
with transaction("app.db") as conn:
    conn.execute("INSERT INTO users (name) VALUES (?)", ("ada",))
    conn.execute("INSERT INTO audit (action) VALUES (?)", ("signup",))
# both rows committed, or neither; connection always closed

Compare that with the manual version and the value is obvious: the cleanup policy lives in one place, and every caller gets it right by construction.

Common Pitfalls

Forgetting that __exit__ sees exceptions, not results. The three arguments describe a failure, not the block's return value. If you need the result, capture it inside the block.

Over-suppressing. Returning True from __exit__ swallows exceptions silently. Reserve that for narrow, documented cases like suppress(), never as a default.

Doing real work in __enter__ that can fail halfway. If setup itself needs cleanup, wrap it in try/except inside __enter__ so a partial setup does not leak.

Wrapping Up

The with statement is Python's answer to a universal problem: resources must be released, and humans forget. Context managers move that responsibility from every call site into one well-tested object. You have used them since your first file tutorial; now you can recognize the pattern in locks, transactions, and temporary state, and you can build your own in five lines with contextlib.
